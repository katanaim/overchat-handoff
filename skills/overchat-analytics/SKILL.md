# Overchat Product Analytics

Цель скилла: по запросу Лизы (founder/PM Overchat) собрать **корректный SQL для BigQuery GA4** без типовых ошибок, а после того как она вернёт JSON-результат в чат — построить **понятные таблицы** с продуктовыми инсайтами и пометками где нужно обратить внимание.

Рабочий цикл всегда: **написать SQL → Лиза прогоняет в BigQuery и кидает JSON → обработать (обычно в Python/bash) → выдать таблицы + выводы.** Claude сам SQL не выполняет и на живой сайт не ходит.

Отвечать Лизе по-русски, в её стиле (по делу, без воды, цифры точные/не округлённые где важно). Отчёты должны быть пересылаемы начальству: эмодзи-заголовки секций, абсолютные числа + проценты, явные ⚠️-флаги проблем.

## Перед ЛЮБЫМ запросом

1. **Узнать сегодняшнюю дату** (она дрейфует — Лиза ловила на устаревших датах). От неё считать окна.
2. **Прочитать `references/database-schema.md`** — двойная схема, дедуп, NULL-ловушка, URL-карта. Это главный источник ошибок.
3. **Вставить `excluded_users` CTE** из `assets/excluded_users_cte.sql` первым CTE в каждый запрос (вербатим, диапазон дат под период).
4. Готовые проверенные запросы — в `references/sql-templates.md`. Цены/доход — в `references/pricing-revenue.md`.

## Окна сравнения по времени (дефолт)

Когда просят «сравни недели» / изменения по времени, без явных дат:
- **LAST (прошлая неделя)** и **PREV (позапрошлая)** — два смежных 7-дневных окна.
- **Буфер 2 дня** от сегодняшней даты (GA4-экспорт догоняет с лагом). То есть `LAST_END = сегодня − 2 дня` (или ближайшее воскресенье с тем же смыслом), `LAST_START = LAST_END − 6`, `PREV_END = LAST_START − 1`, `PREV_START = PREV_END − 6`.
- Всегда озвучивать выбранные даты в ответе.

## ⚠️ Два жёстких правила сравнения (Лиза на этом ловит)

1. **Воронки между неделями сравнивать по КОНВЕРСИЯМ, а НЕ по абсолютным числам.** Абсолюты при сравнении воронки бесполезны: если трафик упал на 32%, все абсолютные шаги механически падают на ~32%, и колонка Δ просто повторяет «−32%» — это мусор. Считать **разницу конверсий в процентных пунктах (п.п.)**: `Δ п.п. = конверсия_LAST − конверсия_PREV`. Так видно, изменилось ли ПОВЕДЕНИЕ (а не объём).
2. **Трафик по виджетам сравнивать в АБСОЛЮТНЫХ числах** (визиты PREV vs LAST) + Δ%. Тут абсолюты как раз нужны.

Абсолютные числа в воронке тоже показывать (для контекста и расчёта), но вывод о «лучше/хуже неделя» делать ТОЛЬКО по сдвигу конверсий в п.п.

## Запрос «посмотри воронку <виджета/фичи>» — полный протокол

Лиза под «воронкой» имеет в виду ПОЛНУЮ воронку по ВСЕМ событиям, а не 4 шага. Делать так:

### Шаг 1. Пропылесосить ВСЕ события
Запросом-палитрой (sql-templates.md → шаблон 1) вытащить **все** события и на лендинге (`/image|video|...`), и в продукте (`/web/...`), за оба периода. Имена событий у каждого виджета свои — **не угадывать**, брать из палитры. Если продукт-URL неизвестен — широкий токен + классификация surface; если продукт не находится под токеном (как attractiveness) — найти отдельным запросом «куда уходят» (шаблон 5).

### Шаг 2. Построить ПОЛНУЮ воронку по найденным событиям
Для **каждого** осмысленного шага (визит → клик загрузки → загрузка → клик генерации → переход в продукт → пейволл показан → пейволл клик → регистрация → генерация → покупка — реальный набор берётся из палитры) дать:
- **абсолютное число** (уникальных юзеров),
- **конверсию** (% от визита и/или % от предыдущего шага),
- **трафик на странице** (визиты лендинга и/или вход в продукт как база).

⚠️ Шаги воронки бывают НЕ строго вложены (пейволл в продукте может быть > генерации на лендосе, т.к. это разные поверхности и юзер может попасть на пейволл минуя генерацию). Если строишь «сужающуюся» воронку — делай строго вложенные шаги по времени (sql-templates.md → шаблон 3). Если показываешь частотную картину (был ли шаг вообще) — честно помечай, что это не строгая последовательность. Всегда флагать аномалии типа «шаг N+1 больше шага N».

### Шаг 3. Разбивка покупок по типам + доход
- Разбить покупки по планам (onetime/weekly/monthly/yearly/creator/studio) — абсолютные транзакции.
- Посчитать **доход** по зашитым ценам USD (references/pricing-revenue.md).
- Дать **средний чек** и **$ на 1000 визитов**.
- Указать **способ оплаты** (apple/universal) если релевантно; флагать резкие сдвиги (возможен сломанный чекаут).

### Шаг 4. Отдельная под-воронка пост-онбординг модалки
Вытащить ВСЕ события содержащие `post-onboarding` (имена варьируются по виджетам: `timer-armed`, `impression`, `cta-<target>`, `view-<target>` и т.п.). Построить мини-воронку: модалка взведена → показана → показ промо-карточки → клик CTA. Посчитать насколько хорошо конвертит (CTR промо, % дошедших). Это отдельный блок в отчёте.

### Шаг 5. Если просят сравнение недель — наложить правило конверсий
Каждый шаг: конверсия PREV vs LAST + **Δ в п.п.** Доход и микс планов — PREV vs LAST. Вывод о здоровье воронки — по сдвигу конверсий, не по абсолютам.

## Формат вывода (для всех задач)

- **Таблицы** с абсолютами и процентами. Шаги воронки — сверху вниз, с конверсией каждого перехода.
- **Эмодзи-заголовки** секций (🔬 воронка, 💰 доход, 📉/📊 трафик, 🎯 вывод, ⚠️ внимание).
- В конце — короткий блок **«🎯 Вывод»** (1-2 абзаца: что произошло) и **места внимания** (⚠️ что чинить/копать), отсортированные по влиянию на деньги.
- **Честность по данным:** флагать малые выборки (единицы покупок → конверсии дрожат), несходящиеся числа (покупатели ≠ транзакции), кривую генерацию (маска не поймала), утечку продукта на другой URL. Лиза ценит флаги ошибок данных выше красивых цифр.
- **Не подавать Δ абсолютов как сравнение воронки** (см. правило выше).

## Частые грабли (чтобы запрос не падал и не врал)

- **NULL-ловушка:** никогда `AND NOT(action='...')` / `action != '...'` в WHERE при NULL-полях — молча роняет все page_view и лендинг-события. Чистить шум в Python. (database-schema.md)
- **GROUP BY по алиасу:** группировать по исходному полю, не по алиасу с префиксом (`Name X not found inside p`).
- **Дедуп:** `event_name != 'user_id_pushed'` в SQL; UUID-чаты и слитые дубли — в Python; при сведении брать MAX(users), не сумму.
- **Двойная схема:** лендинг — семантика в `event_name`; продукт — в `eventCategory/Action/Label` при `event_name='overchat'`.
- **Только web:** мобильных данных в BigQuery нет.
- **Буфер дат:** не брать последние ~2 дня (неполный экспорт).
